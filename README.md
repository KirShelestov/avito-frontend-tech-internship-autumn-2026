# BookRoom: система бронирования переговорных

Веб-приложение, в котором сотрудник выбирает офис, находит свободную переговорную на
нужное время, бронирует её и управляет своими бронированиями. Расписание комнаты и
список доступных комнат обновляются в реальном времени через WebSocket.

Тестовое задание Frontend, осенняя волна 2026. Основная работа лежит в папке `client/`.

## Структура репозитория

- [`client/`](./client): веб-приложение на React + TypeScript + Vite. Это и есть решение задания.
- [`server/`](./server): предоставленный mock-backend (REST + WebSocket + тестовые данные).
- [`images/`](./images): макеты интерфейса.
- [`Frontend-trainee-assignment-autumn-2026.md`](./Frontend-trainee-assignment-autumn-2026.md): текст задания.

## Запуск

Нужен Node.js 20 или новее. Бэкенд и клиент поднимаются в двух терминалах:

```bash
# терминал 1: бэкенд
cd server
npm ci
npm run dev            # http://localhost:3000

# терминал 2: клиент
cd client
npm ci
cp .env.example .env
npm run dev            # http://localhost:5173
```

Откройте `http://localhost:5173`. Клиент ждёт бэкенд на порту `3000`, адреса задаются
через `.env` (см. `client/.env.example`).

### Через Docker

Всё поднимается одной командой; исходники примонтированы в контейнеры, поэтому
hot-reload работает как при локальном запуске:

```bash
docker compose up            # фронт на :5173, API на :3000
docker compose up --build    # пересобрать образы после изменений в package.json
docker compose down
```

Порты `3000` и `5173` на хосте должны быть свободны.

### Разработка без бэкенда

Поставьте `VITE_USE_MSW=true` в `client/.env`, и все запросы (REST и WebSocket) обслужит
мок-слой на MSW с теми же сценарными данными, что и в тестах.

## Технологии и почему они

- **React 18 + TypeScript (strict) + Vite 5.** Быстрый dev-сервер, из коробки дружит с
  Vitest и Storybook.
- **react-router-dom v6**, data-router (`createBrowserRouter`). Маршруты `/rooms`,
  `/rooms/:roomId`, `/bookings`, редирект `/` → `/rooms`, страница 404 на всё остальное.
  Страницы грузятся отдельными чанками (`React.lazy`).
- **TanStack Query v5** для серверного состояния: кэш, дедупликация запросов, `isLoading`/
  `isError` из коробки, точечная инвалидация по WebSocket-событиям.
- **react-hook-form + zod**: формы и валидация. Доменные правила (шаг 15 минут, рабочие
  часы, горизонт 30 дней) продублированы на клиенте, финальную проверку делает бэкенд.
- **Luxon**: даты и таймзоны. Всё время показывается в таймзоне офиса, вычисления идут
  от `office.timezone`, а не от часового пояса браузера.
- **Radix UI**: доступные примитивы (диалог, поповер, табы, тосты), из коробки фокус-трап, Esc,
  корректные `aria-*`.
- **Emotion** (`@emotion/styled`) + дизайн-токены на CSS-переменных. Инлайновые `style`
  не используются, стили компонента лежат в соседнем `*.styles.ts`.
- **i18next**: все пользовательские строки вынесены в словарь `shared/i18n/locales/ru.ts`.
- **Vitest + Testing Library + MSW** для юнит- и компонентных тестов.
- **Playwright** для end-to-end против настоящего бэкенда.
- **Storybook 8**: UI-кит и состояния экранов в изоляции.

Тяжёлые UI-киты (MUI, AntD) и Redux сознательно не брались: первые не бьются с макетом,
второй избыточен: серверное состояние закрывает Query, а фильтры живут в URL.

## Архитектура

Слоистая структура в духе Feature-Sliced Design:

```
src/
  app/       инициализация: провайдеры, роутер, error boundary, глобальные стили
  pages/     экраны под маршруты, держат состояния loading / error / empty
  widgets/   крупные самостоятельные блоки: Header, RoomSchedule, RoomsFilterBar
  features/  пользовательские сценарии: создание и отмена брони, real-time, экспорт .ics
  entities/  доменные сущности: типы, query-хуки, «тупые» карточки (room, booking, office)
  shared/    переиспользуемое без доменных знаний: ui-kit, api (http/ws), lib, config
```

Импорты идут только вниз: `app → pages → widgets → features → entities → shared`.

**Поток данных.** Компоненты читают серверные данные через query-хуки в `entities/`
(`useRooms`, `useRoomSchedule`, `useMyBookings`). Мутации (`useCreateBooking`,
`useCancelBooking`) после успеха инвалидируют затронутые ключи. Ключи собраны в одном
месте, в `shared/api/queryKeys.ts`.

**Real-time.** `RealtimeProvider` держит одно WebSocket-соединение и превращает каждое
событие в инвалидацию соответствующих query-ключей, а не в ручной патч кэша. Это
проще и совпадает с моделью бэкенда, где источник истины REST. Всплеск событий
(`booking.*` и следом `room.availability_changed`) схлопывается debounce'ом на 150 мс.
Соединение переподключается с экспоненциальным backoff; при обрыве показывается жёлтый
баннер, а после восстановления все активные запросы перечитываются заново, потому что
журнала пропущенных событий у бэкенда нет. Событие `data.reset` очищает кэш целиком.

## Тесты

```bash
cd client

npm test                 # юнит и компонентные (Vitest), ~190 тестов
npm run coverage         # то же с отчётом покрытия (ориентир 80%+, сейчас ~96%)
npm run e2e              # end-to-end (Playwright) против server/ на :3000
npm run storybook        # UI-кит и экраны в Storybook
npm run check            # формат + линт + типы + юнит-тесты одной командой
```

Перед первым запуском e2e один раз поставьте браузер: `npx playwright install chromium`.
Playwright сам поднимет бэкенд и клиент (или переиспользует уже запущенные) и перед
каждым тестом сбрасывает данные через `POST /api/v1/test/reset`.

Пирамида: много юнит-тестов на `shared/lib`, `http`/`ws`, zod-схемы и маппинг
WebSocket-событий; компонентные тесты на каждый экран во всех состояниях и на обработку
конфликта `409`; сверху 9 сквозных сценариев в реальном браузере.

## Принятые решения

- **Чужие брони в расписании показываются как «Занято»** без темы встречи ради приватности.
  Свои видны с заголовком.
- **Состояние фильтров живёт в URL** (`?office&date&start&duration&capacity`). Ссылку
  можно переслать, и экран восстановится один в один.
- **На WebSocket-события отвечаем инвалидацией**, а не патчем кэша. Точечный патч стал бы
  лишним источником рассинхрона с бэкендом.
- **`data.reset`** → полная очистка кэша, перезапрос активных данных, тост «Данные
  обновлены».
- **Горизонт 30 дней и рабочие часы 09:00–20:00** считаются в таймзоне офиса. Даты вне
  окна в календаре недоступны, `TimeField` не даёт ввести время не по 15 минут,
  длительность обрезается так, чтобы бронь заканчивалась не позже 20:00.
- **Строка «Занята до 15:30 / Свободна весь день»** на карточке комнаты: API её не отдаёт,
  поэтому для каждой комнаты подгружается расписание на выбранный день. Ключи кэша общие
  со страницей комнаты, так что real-time обновляет и их.
- **Фильтр периода в «Моих бронированиях»** работает на клиенте: у `GET /bookings` есть
  только `scope` и `officeId`.
- **Клиент не рвёт «тихое» WebSocket-соединение по таймауту.** Бэкенд шлёт протокольные
  ping-фреймы, а браузерный `WebSocket` их не показывает, поэтому обрыв ловится по `close`.
- **Шрифт Manrope** подключён локально через `@fontsource-variable/manrope`, без запросов
  к Google Fonts.
- **Отмена брони оптимистична**: карточка исчезает сразу, при ошибке возвращается на
  место с тостом.
- **Повторяющиеся брони** клиент разворачивает в серию дат и шлёт по одному
  `POST /bookings` (бэкенд про серии не знает). Частичный успех показывается сводкой
  «создано K из M, конфликты: …». Принадлежность к серии хранится локально.
- **При первом заходе без выбранного офиса** показывается экран «Выберите офис», а фильтры и список
  неактивны, пока офис не выбран.
- **Одно изменение в предоставленном бэкенде.** В `server/src/app.ts` в конфигурации
  CORS явно перечислены методы (`GET, HEAD, POST, DELETE`). В `@fastify/cors` v11
  по умолчанию разрешены только `GET, HEAD, POST`, из-за чего preflight на
  `DELETE /api/v1/bookings/:id` падал в браузере и отмена брони не работала.

## Что сделано сверх обязательного минимума

- Reconnect с экспоненциальным backoff, resync после обрыва и индикатор состояния
  соединения в шапке и баннером.
- Real-time обновление не только открытого расписания, но и всего списка комнат.
- Оптимистичная отмена брони с откатом.
- Экспорт брони и всех предстоящих броней в файл `.ics`.
- Повторяющиеся бронирования (ежедневно / еженедельно / по будням).
- Storybook с UI-китом и состояниями экранов, MSW как единый слой моков для Storybook,
  тестов и разработки без бэкенда.
- Доступность: фокус-трапы в модалках, `aria-live` для тостов и баннера, навигация с
  клавиатуры, поддержка `prefers-reduced-motion`.
- Error boundary со страницей «Что-то пошло не так», `document.title` под каждый экран,
  скролл наверх при переходах, code-splitting по маршрутам.
- Dockerfile и docker-compose для клиента и бэкенда.

Подробности по клиенту (скрипты, переменные окружения, слои) лежат в
[`client/README.md`](./client/README.md).
